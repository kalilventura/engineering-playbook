# Engineering Playbook

> Software engineering principles for AI-assisted development.

A collection of practices, reusable AI-agent instructions, and workflows to help teams build **maintainable, testable, well-architected** software — even when most of the code is generated by an agent.

## Why this exists

AI agents generate code fast, but fast isn't the same as well designed. Without explicit standards, it's easy to end up with unnecessary abstractions, business logic leaking into infrastructure, weak tests, and risky refactors.

This repository is the shared engineering context between developers, reviewers, and AI agents — not a framework, just decision-making principles.

## How it's organized

- **`AGENTS.md`** — entry point for AI agents: how to understand, classify, and implement a change following this playbook.
- **`PLAYBOOK.md`** — central index of principles.
- **`skills/`** — reference knowledge an agent consults to make a decision (`clean-architecture`, `clean-code`, `go-conventions`, `testing-practices`, `event-driven-messaging`, `observability-logging`, `safe-refactoring`, `engineering-governance`, `context7-mcp`, `docker-compose-layered`, `documenting-api-endpoints`). Each is a `SKILL.md` in the Claude Code skill format.
- **`commands/`** — processes triggered explicitly rather than consulted continuously (`code-review`, `ci-pipeline`, `autofix`, `test-automation`, `deployment-gates`).

## Core principles

1. **Understand before changing** — inspect the existing code, tests, and conventions before proposing anything.
2. **Prefer the smallest coherent change** — don't rewrite a whole module to fix a small problem.
3. **Keep responsibilities separated** — business rules shouldn't depend on HTTP, databases, Kafka, storage, etc.
4. **Use abstractions only when needed** — an interface should represent a real boundary, not exist just to enable a mock.
5. **Tests are part of the design** — unit, integration, and e2e tests serve different purposes; don't conflate them.
6. **Automation reinforces standards, not bypasses them** — an agent should never fix a broken pipeline by disabling a test, gate, or validation.

## Using it in a project

- **Simplest:** copy `AGENTS.md` into the project root and reference the playbook.
- **Shared across projects:** include this repository as a git submodule.
- **Tailored:** copy only the relevant skills/commands (e.g. a Go/Kafka project likely only needs `skills/clean-architecture`, `skills/clean-code`, `skills/go-conventions`, `skills/testing-practices`, `skills/event-driven-messaging`, `skills/observability-logging`, `skills/docker-compose-layered`, `skills/documenting-api-endpoints`, and `commands/code-review.md`).

Details for each area live in `skills/`, `commands/`, and `PLAYBOOK.md`.

## Contributing

When adding a new skill or command: focus on one concern per file, explain the principle before the implementation, prefer concrete examples, and state when the rule applies (and when it doesn't). A new rule only earns its place if it improves decisions, not just adds to the count.
